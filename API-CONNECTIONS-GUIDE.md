# SHOPYHAT — API Connections (Provider-neutral)

The Reseller & Fulfillment Studio → **API Connections** module is intentionally not tied to any courier.

## Outbound: SHOPYHAT connects to another service
1. Open **Admin → Resellers → API Connections → Outbound**.
2. Add a clear connection name, official HTTPS API base URL, and a harmless GET status endpoint (e.g. `/health`, or the provider's documented account-check endpoint). Do **not** test an order-creation endpoint.
3. Choose one of these standard header-based auth methods: None, Bearer Token, single API Key header, or Key + Secret headers.
4. Enter the API credentials and Save. They are encrypted by Supabase Vault; SHOPYHAT displays connection metadata but **never returns stored secrets**.
5. Click **Test Connection**. Only a GET connectivity check is performed. A successful test does not imply booking, label creation, COD reconciliation or webhooks are implemented.
6. To change a connection, click Edit Settings. Leave key/secret blank to retain existing credentials. Disable to stop using it.

**Important:** Provider-specific operations such as create parcel, print label, cancel, track or reconcile are *not* automatically generated by entering arbitrary endpoints. These require an explicit adapter for each provider's API schema, supported authentication method and required customer consent. The earlier Steadfast-only configuration has been replaced in the Admin UI; the historical dedicated function is not used by this module.

## Inbound: a third party connects to SHOPYHAT
1. Open **Inbound** and enter the partner/company name.
2. Click **Generate Partner API Key**.
3. Copy the one-time key and send it privately over a trusted channel; SHOPYHAT stores only its SHA-256 digest, and cannot re-display the original.
4. Partner calls `GET https://xwfqgmgiunlxzvzoermn.supabase.co/functions/v1/shopyhat-partner-api/health` with header `x-shopyhat-api-key: <issued key>`.
5. **Revoke** the partner's key in Admin immediately if compromised or no longer required. Issue a new key rather than recovering the old one.

For safety, inbound partners currently have access only to a health check. **No order read/write, customer information, courier booking or webhooks are enabled**. Future integrations should receive explicit scoped permissions, request signing, rate limiting, webhook audit logs, and their own API contracts.

## Credentials and security
- Never put service-role keys, provider secret keys or SHOPYHAT partner API keys in public HTML or product pages.
- Owner/Manager permissions are checked on the backend for integration administration.
- The application stores outbound credentials encrypted in Supabase Vault, not in browser storage.
- Endpoints must be publicly resolvable HTTPS domains, direct paths and no redirects; private/local IP destinations are blocked as a best-effort SSRF defense.
- Connection tests have a short timeout and do not trigger shipment creation.
- Third-party service prices and account requirements are determined by that provider, not by SHOPYHAT.

## Reseller contextual filters
- **Requests**: request date, status, applicant name, company, phone or email.
- **Accounts**: registration date, approval status, business name, login ID, mobile or shop alias.
- **Fulfillment**: request date, fulfillment status, customer name/mobile/address or reseller ID.
- **Referral Sales**: attribution date, referral status, order ID or reseller ID.
- Each section has relevant status choices, search, date presets and Clear Filters.
- **Product Pricing** is independent: product search, enabled/disabled and server pagination.
- Reseller **Product Catalog** search has a short debounce and avoids outdated query results.

## Authentication setting
For password-only customer signup with **no OTP and no signup confirmation**, keep Email Provider enabled and confirm the project-level **Confirm Email** requirement is disabled. The supplied Email Provider screenshot does not display this setting. Password reset email remains a separate recovery security control. Instant signup without email ownership verification increases fake-account/recovery risks, so rate limiting and password requirements should remain enabled.
